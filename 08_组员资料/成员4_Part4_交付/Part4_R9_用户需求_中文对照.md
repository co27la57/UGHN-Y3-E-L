## 9. 用户需求及其论证

以下十条需求说明 ID-Coo 必须为目标农场做到什么。它们是**用户需求，而非设计方案**——只说明必须达成什么，不说明如何实现（实现方式见第 10 节）。每条均单独论证，并分别追溯到第 1 节的法规约束、第 2 节的误识别后果，以及第 3 节的客户任务、痛点与收益。在 MoSCoW 框架下**全部为 Must have**：每一条都是价值主张的前提条件，在第一版中不可取舍。

| 编号   | 用户需求（系统必须做到什么）                 | 论证与追溯                                                       |
| ---- | ------------------------------ | ----------------------------------------------------------- |
| UR1  | 对每一头携带兼容且有效电子耳标的牛，确认其身份        | 记录绑定错误会破坏治疗、产奶与繁殖数据，并削弱奶款收购方的管控（§2）；可靠的身份对应是客户的核心收益（§3）     |
| UR2  | 将每一头无法确认身份的牛，纳入可管理的复核流程        | 耳标会丢失、损坏或无法读取（五年累计 19.8% [6]）；身份未知的牛不得悄然回到牛群，也不得在猜测的身份下记录   |
| UR3  | 绝不把同时通过的两头及以上的牛按单头处理           | 牛过通道门时会相互紧跟，可能一次产出两个编号；把邻牛编号绑定到当前牛是误识别的直接原因（§2）             |
| UR4  | 让人员能在通道外操作、停止并安全接管系统           | 牛只处理对人畜都有受伤与应激风险 [8]；第一版依赖人员确认单头进牛，因此外部操控是安全使用的前提           |
| UR5  | 让每条读数始终绑定产生它的牛，并确认实际走过的出口      | 延迟的结果绝不能作用于下一头牛，正确的读数也绝不能分流错牛——两者都是有记录的失效路径（§2）             |
| UR6  | 断网时仍保留通行与异常记录                  | 农场网络不可靠；记录必须在断网期间保存，以便之后完成核验与申报（§3：记录分散）                    |
| UR7  | 提供可审计的身份、时间与结果记录，且不误报法定移动      | 法定义务包括 36 小时内更新场所登记册、3 天内申报移动 \[4\]\[5]；通道内的内部通行绝不能申报为场所间转移 |
| UR8  | 在约定吞吐量下不造成不可接受的排队              | 保持通行顺畅是明确的客户任务（§3）；试验目标为 90 分钟内处理 200 头，计入重读与常规复核           |
| UR9  | 经常规清洁后，在农场环境（潮湿、污秽、低温、腐蚀）中持续运行 | 在真实牛舍中的稳健性、可靠性与可维护性是明确的产品要求（§1）；设备必须适应真实条件，而非只适应实验室         |
| UR10 | 使总拥有成本与经过验证的经济收益相匹配            | 可负担性是明确要求：价格必须以"物有所值"证明，并以实测而非声称的劳动节省为证据（§12）               |

UR1 的验收要求将**已确认读数的正确率**与**覆盖率**分别报告：若仍有大量牛只身份未解决，仅凭已确认读数的高正确率并不能证明识别充分。
